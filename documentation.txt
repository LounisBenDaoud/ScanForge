# Documentation des Scripts Principaux (Core) du Scanner de Vulnérabilités

Ce document explique le rôle et le fonctionnement des principaux scripts situés dans le dossier `backend/core/`.

## 1. common.py (Fonctions Communes et Base de Données)
Ce script est le pilier central qui contient toutes les fonctions utilitaires partagées par les autres modules du scanner.
- **Gestion des URLs :** Fournit des fonctions pour normaliser les adresses web (`normalize_target_url`), déterminer l'origine (`get_origin`) et définir la portée du scan (`get_scope_root`, `same_origin`).
- **Réseau :** Permet de créer une session HTTP configurée (`build_session`) avec des en-têtes personnalisés (comme un User-Agent spécifique) et de gérer les cookies pour l'authentification.
- **Base de données :** Contient la logique d'interaction avec la base de données SQLite (fichier `scanner.db`). Il gère la connexion, la création/récupération de la cible, le démarrage/l'arrêt des scans, et surtout, l'ajout des vulnérabilités trouvées via la fonction `add_vulnerability()`.

## 2. recon.py (Reconnaissance HTTP)
Ce module analyse la configuration de sécurité exposée par la cible.
- **En-têtes et cookies :** Il vérifie les en-têtes de sécurité, la qualité de la CSP, les attributs des cookies et les informations de version divulguées. HSTS n'est signalé que pour une cible HTTPS et `frame-ancestors` est reconnu comme protection anti-cadrage.
- **Vérifications actives limitées :** Il envoie une origine CORS non fiable, contrôle les méthodes annoncées par `OPTIONS`, valide réellement `TRACE` et recherche les erreurs verbeuses ainsi que le contenu mixte HTTPS/HTTP.
- **Rapport :** Chaque résultat contient une preuve, une criticité et une recommandation adaptée.

## 3. fuzzer.py (Découverte de Contenu Caché)
Le but de ce script est de trouver des répertoires, des fichiers sensibles ou des chemins d'administration cachés qui ne sont pas référencés publiquement sur le site.
- **Découverte hybride :** Il combine la liste `wordlist.txt` avec les chemins trouvés dans HTML, JavaScript, `robots.txt` et les sitemaps. Les requêtes sont parallélisées tout en restant bornées par le profil choisi.
- **Gestion Intelligente des Faux Positifs :** Pour contourner les serveurs qui renvoient des codes "200 OK" même quand une page n'existe pas (Custom 404), il génère d'abord plusieurs requêtes vers des pages aléatoires ("baselines"). Il compare ensuite le statut, le titre, la taille et le contenu des réponses. Une route correctement protégée par HTTP 401/403 et une API publique ordinaire ne sont plus comptées comme vulnérabilités.
- **Classification fondée sur la preuve :** Un résultat n'est enregistré que si le contenu, le nom du chemin ou une indexation de répertoire fournit un indice de sécurité concret. Les fichiers sensibles, secrets, journaux, métriques et données personnelles reçoivent une criticité adaptée.

## 4. payloads.py (Tests d'Injections XSS et SQL)
C'est le module le plus complexe et offensif, conçu pour simuler des attaques d'injection de code sur l'application web.
- **Crawling et Découverte de Paramètres :** Le moteur extrait les liens, formulaires et scripts, puis complète les candidats depuis JavaScript, OpenAPI/Swagger et des conventions API génériques. Il sait aussi lire un document OpenAPI incorporé dans `swagger-ui-init.js`, élimine les copies identiques d'une page de démarrage SPA et rejette les erreurs de route produites par les frameworks.
- **Test Cross-Site Scripting (XSS) :** Il recherche les XSS réfléchies dans les réponses HTTP et les XSS DOM dans les applications SPA. Pour les routes placées après `#`, qui ne sont jamais envoyées au serveur, le scanner ouvre la page dans Chrome, Chromium ou Edge en mode headless. Il confirme l'exécution par une modification contrôlée du DOM ou, si un filtre modifie ce payload, par l'ouverture d'un dialogue JavaScript comparée à une navigation témoin. Si aucun navigateur compatible n'est disponible, l'analyse statique reste classée comme potentielle.
- **Test d'Injection SQL (SQLi) :** Il tente de manipuler les requêtes SQL selon quatre techniques et exige des comparaisons répétables pour limiter les faux positifs :
  1. *Error-based SQLi :* Injection de caractères provoquant la casse de la requête (comme les guillemets simples `'`) pour déceler des messages d'erreur de base de données visibles publiquement.
  2. *Boolean-based Blind SQLi :* En l'absence de messages d'erreur explicites, il va envoyer des expressions booléennes vraies puis fausses (ex: `OR 1=1` vs `AND 1=2`) et analyser les différences de comportement de la page (nombre de résultats, différence de contenu/statut HTTP) pour prouver l'injection.
  3. *UNION-based SQLi :* Il recherche un nombre de colonnes compatible puis vérifie qu'un marqueur provient réellement de la requête SQL et non d'un simple écho HTTP.
  4. *Time-based Blind SQLi :* Il compare deux mesures du délai injecté à une requête témoin propre avant de confirmer le résultat.

## 5. Profondeur et portabilité
Les profils `Léger`, `Standard` et `Approfondi` règlent réellement le nombre de pages, chemins, scripts, candidats et tests temporels. La découverte générique est exécutée avant les chemins de compatibilité connus : le scanner n'est donc pas limité à Juice Shop ou DVWA. Un résultat n'est cependant affiché que lorsqu'une preuve observable est obtenue ; il ne fabrique pas une vulnérabilité pour atteindre un nombre attendu.
